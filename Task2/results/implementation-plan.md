# Верхнеуровневый план конфигурации и имплементации модуля пакетной обработки данных

**Kubernetes CronJob** с контейнером-экспортёром, который читает
PostgreSQL и выгружает кастомные CSV/XLS прайс-листы в Object Storage.

## Предварительные условия и решения

- Согласовать стек экспортёра: лёгкий скрипт (Python/Go).
- Завести в БД отдельного **read-only пользователя** для выгрузки.
- Определить целевое Object Storage (S3/MinIO) и бакет/префикс для прайс-листов.
- Определить формат: CSV обязателен, XLS/XLSX - опционально на клиента.
- Определить получателей уведомлений (Email/вебхук) и канал алертов (Alertmanager/Slack).

## Разработка модуля-экспортёра

1. Модуль читает конфигурацию из env/args (строка подключения, бакет, форматы, TZ).
2. Выполняет join (через view/SQL), обходит клиентов, для каждого пишет CSV/XLS.
3. Публикует файлы в Object Storage по ключу `pricelists/<YYYY-MM-DD>/client_<id>.<ext>`.
4. Пишет структурированные логи (JSON в stdout) и метрики (счётчики строк/файлов,
   длительность, ошибки).
5. Возвращает ненулевой код выхода при ошибке (для retry на уровне Job).
6. Покрывается unit-тестами (join, форматирование, дедупликация) и интеграционным
   тестом на тестовой БД.

## Контейнеризация

1. Multi-stage `Dockerfile`, non-root пользователь, фиксированные версии зависимостей.
2. Небольшой базовый образ (distroless/alpine) для быстрого старта и меньшей поверхности атаки.
3. Публикация образа в registry с тегом версии (semver/git-sha).

## Конфигурация Kubernetes

1. **Namespace** `pricing` (или в существующем).
2. **ServiceAccount** + минимальные RBAC-права (в идеале права на Job не нужны, только
   доступ к секретам/бакету).
3. **Secret** для доступа к БД (через External Secrets / Workload Identity / IRSA -
   без хранения паролей в манифестах).
4. **ConfigMap** с параметрами (SQL/view, форматы, TTL, бакет).
5. При необходимости - `PriorityClass` и `nodeSelector`, чтобы ночная выгрузка не
   конкурировала с онлайн-трафиком.

## Доступ к данным и безопасность

1. Read-only пользователь БД, TLS-подключение, ограничение по объектам.
2. Секреты - только через Secret/External Secrets; ротация и аудит.
3. Доступ к бакету - через IAM-роль пода (Workload Identity/IRSA), без статических ключей.

## Логирование и мониторинг

1. Логи пода → Loki/ELK (единый контур магазина).
2. Метрики Job → Prometheus: `kube_job_status_failed`, `kube_job_status_succeeded`,
   длительность, число строк/файлов.
3. Алерты в Alertmanager: падение Job, превышение `activeDeadlineSeconds`, пустой результат.
4. Дашборд в Grafana: история ночных выгрузок, объём, время выполнения.

## Доставка и уведомления

1. Notification Service рассылает клиентам ссылки/вложения (Email/HTTPS).
2. Уведомление менеджеров о завершении/ошибке.
3. Опционально - публикация ссылок в B2B-портал клиента.

## Тестирование и приёмка

1. Unit-тесты логики экспортёра.
2. Интеграционный тест на тестовой БД с репрезентативным объёмом.
3. E2E в staging: ручной запуск Job (`kubectl create job --from=cronjob/price-list-export`)
   и проверка файлов/метрик/алертов.
4. Проверка идемпотентности повторного запуска и поведения при недоступности БД.

## Эксплуатация

1. Ручной backfill/перезапуск через разовый Job из CronJob.
2. Ретенция файлов в Object Storage (lifecycle-политика).
3. Мониторинг стоимости и объёма; при росте нагрузки - `parallelism`/шардирование клиентов.
4. Runbook для типовых инцидентов (недоступна БД, пустая выгрузка, ошибки доставки).
